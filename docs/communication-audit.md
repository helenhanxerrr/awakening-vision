## 帧与传输

| 方向 | 格式 | 总长度 |
| --- | --- | --- |
| 视觉 → 控制 | int16 长度 16；int16 ID 1 + float yaw/pitch；int16 ID 2 + int32 fire_flag | 18 字节 |
| 控制 → 视觉 | int16 长度 28；int16 ID 1 + float yaw/pitch/roll + int32 mode/robot_id；int16 ID 2 + float bullet_speed | 30 字节 |

小端，角度单位度，无 CRC、同步帧头或握手。固件通过 USB CDC/VCP 收发，视觉配置为 `/dev/ttyACM0`、115200、8N1；设备路径必须按实际枚举确认。`color` 字段实际装的是机器人 ID。

固件 `DecodeVision(uint16_t recv_len)` 未使用实际长度，`get_srm_protocol_info` 按 64 字节容量处理输入。本次直接运行原版固件解析代码，复现：

- 两条 18 字节控制帧合在一次回调内时，仅第一帧被消费。
- 仅收到前 8 字节时，解析器仍读取缓冲区后续内容，可能把残留字节写入控制字段。

视觉侧逐帧 `async_write` 不保证操作系统和 USB 保持同样的分包边界。无法只修改视觉端就彻底消除上述接收端缺陷；要解决，需要控制端维护者按 `recv_len` 缓存输入并循环消费完整帧。此任务没有修改控制端。

通信收到命令也不等于执行命令：云台和发射机构仍受固件遥控挡位、摩擦轮状态和分支逻辑约束；导航消息未注册。本次没有验证运动或发射。

## 本次修复

`serial_driver.hpp` 原先在验证前透传原始接收字节，驱动重连重置自身解析器时，业务层的第二个解析器仍可能保留旧半包。现在配置了同济 ID 的链路仅投递完整有效帧（保留长度头），半包仅由驱动持有，断线时丢弃；未配置同济 ID 的串口保持字节透传。业务层现有完整帧解析接口不变。

回归测试覆盖非法帧不投递、半包超时后不跨连接拼接、错帧重连后完整帧正常投递，以及非同济串口透传。测试调度器计数改为原子变量，避免测试线程与 IO 线程之间的数据竞争。

## 可重复验证与结果

```sh
python3 tests/run_telemetry_tests.py
python3 tests/run_control_interop_tests.py /path/to/control-2026
```

两项均通过。第一项使用真实 Boost.Asio 驱动、yaml-cpp 与 PTY，覆盖编码、全部拆分位置、10000 帧、重连和退出；业务 logger/scheduler 使用测试桩。第二项将控制端三个文件复制到临时目录，校验固定版本 Git blob SHA，仅替换硬件依赖头文件，编译原版 C 打包/解包函数及原版结构体，与视觉生产编解码器双向互测；同时断言上述已知传输缺陷可复现。两个入口均启用 ASan/UBSan，视觉测试代码启用 `-Wall -Wextra -Werror`。
